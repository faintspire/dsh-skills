# 先出方案，不改代码

这个技能覆盖两类入口：用户明确说「先只出方案」「先别动代码」「只评审」，以及用户贴出常量/配置片段问「你打算怎么改」而**尚未要求改代码**。两种情况本轮唯一允许的产出都是 **提问 + 方案文档**，不是代码。技能就是那条边界：先把事实核实到行号，再把契约问清楚，最后只交文档。

## Steps

1. **复述边界（一句话）**：明确本轮不改任何源码、配置和 yml，只做现状核对与方案。即使用户只说「这两段常量写得太死，你打算怎么改」而没说「先只出方案」，也按此边界走——先在回答开头声明零改动，再用第 4 步把「只出方案还是现在就改」问清楚；不要因为问的是「怎么改」就默认开始改。

2. **先定改动面，再定现状表的维度**。表头固定 `环节 | 位置 | 现状`，但**环节不是固定清单**：按本次改动真正经过的链路自定义，3–6 行，缺哪个环节就写「未发现」而不是省略。下面两张表只是示例，照抄维度就等于漏掉本次真正的旁路。

   例 A（配额/限额类改动）：

   | 环节 | 位置 | 现状 |
   |---|---|---|
   | 限额唯一来源 | `SecurityUtil.java:105-109` | 例：只看角色，admin=50，其他=5 |
   | 出图前校验点 | 每个调用点一行 | 例：`currentCount >= dailyMaxCount` 就推错误帧 return |
   | 配额查询 | `...ServiceImpl.java:160-172` | 例：算 remaining 给前端 |
   | 计数（写入）点 | 每个写入点一行 | key 格式、累加单位（张数/次数）、TTL |
   | 可靠留痕 | 表名 + 远端 DTO | 落库/上报是否与计数解耦 |

   例 B（提示词/常量拼装类改动，用户贴常量求改法时按这套走）：

   | 环节 | 位置 | 现状 |
   |---|---|---|
   | 约束常量 | `AiPromptConstants.java:41-51` / `:57-68` | 两段「【规范】+8 行清单」式祈使句 |
   | 唯一分发入口 | `AiPromptConstants.java:91-100` | `constraintsOf(scene)` 返回**单个 String**，PUBLIC 返回空串 |
   | 拼接点① | `AiDrawingServiceImpl.java:63` | `约束 + 用户prompt`，无任何分隔 |
   | 拼接点② | `DoubaoDrawingServiceImpl.java:48` | 与拼接点①相同 |
   | 旁路链路 | `DoubaoDrawingServiceImpl.java:63-64` | 论文示意图只传原始 prompt，**不拼约束** → 本次不动 |
   | 场景判定 | `AiInteractionStrategy.java:177-179` | biovisart 通道 → ARTWORK |

   用户只贴一个片段时，别只读那一个文件：先用 `grep` 找全分发入口和所有调用点（例如 `pattern="ARTWORK_CONSTRAINTS|MATERIAL_CONSTRAINTS"`，或常量名/方法名），再 `read` 每个命中点前后足够上下文，把「生效路径」和「不生效的旁路」都确认掉。

3. **交叉验证每条结论**：表里每一行都要能对上一条 `grep` 命中或 `read` 结果。拿不准的写「待确认」，不要推测行号。Java 用 `Xxx.java:78-90` 指方法体区间；同一职责存在多处（例如两个 WebSocket 策略类、两个绘图 Service 的拼接点）就每个都列一行，不要只写一个。

4. **用问答工具确认两件事**，不要自己假设：
   - （a）落地范围：现在就改，还是本轮只出方案？选项里写清改动面，例如「现在就改（改动 6 个文件：新增配置类+配额服务，改 VO、两个 WS 策略、getDailyQuota，加 yml 白名单）」「只替换两段常量文本（零 Java 逻辑改动）」「只出方案，先评审（推荐）」。
   - （b）关键契约：数据结构或行为有歧义时必须问，例如「不限次数时 limit/remaining 返回 null」还是返回哨兵值；「PUBLIC 场景的空串是否保持不动」。给推荐项并说明后果。

   调用形如 `ask_user_question`（若会话内只能通过 `run_code` 包装，则为 `tools.ask_user_question`），入参为 `questions: [{ id, header, question, options: [{ label, description }] }]`。两个问题可以在一次调用里并列给出（如 `scope` + `public_scope`），每个选项都写清改动面差异。工具不可用时，退化为对话里的编号问题，并**停下等回答**。

5. **等用户回答后再继续**。用户没明确选择前，既不写代码也不替用户定契约。用户选了「只出方案」后，本轮任何写操作都应被排除。

6. **输出方案文档**。默认直接在回答里给 Markdown；只有用户要求落盘时才写 `.md` 文档文件（文档不算代码改动）。未新建任何文件时，也可以先在你熟悉的文档路径给一份草稿，但正文必须随回答给出。结构固定：
   - 0. 结论（一句话：把什么升级成什么，哪些链路不动）
   - 1. 判定规则（唯一权威，用伪代码写清优先级顺序）
   - 2. 改动清单（文件 → 位置 → 改什么 → 为什么）
   - 3. 契约（字段语义、null 语义、兼容旧数据）
   - 4. 边界与风险（含安全边界，例如域名匹配方式；含「哪些链路不受影响」）
   - 5. 明确不做的事

7. **收尾**：声明「代码零改动」，列出可开工的下一步（或等待评审意见）。用户后续改需求时，按新需求**重写方案**，仍然不动代码，直到用户明确说「开始改」。

## Pitfalls

- **技能里的示例维度不是模板**：早期版本把配额五维写成固定表，遇到「贴出提示词常量问怎么改」只能硬套，反而漏了「唯一分发入口 / 两个拼接点 / 不生效的旁路」。按本次改动面重定义环节，并把旁路链路单列一行、标注本次是否影响。
- **用户没喊「只出方案」不等于要改代码**：贴常量/配置求意见、问「你打算怎么改」，仍然是评审语境。先按第 1 步声明零改动、按第 4 步问范围，再出方案；直接改文件会让这轮评审失效。
- **过度设计是首版的真实失败点**：第一版方案引入了 `XxxProperties` 配置类、`record` 配额对象、biz 层 Service 和 Redis 缓存层，共 6 个文件改动，被用户直接否掉。方案先给**最小改动集**（能不改抽象层就不改），把配置类/缓存层列为「可选项」并说明代价，不要默认塞进去。
- **用户纠正后要整体回退，不是叠加**：用户说「直接做一个通用工具类判定即可」时，上一版的 properties/record/service/缓存层要全部删除，并在方案里写明「净新增只剩 1 个文件」。
- **域名匹配不能用 `endsWith(domain)`**：会放行 `a@sangerbox.com.evil.com`。取 `@` 之后整段做 `equals`。
- **优先级顺序不能反**：特殊后缀 > admin 角色 > 普通用户，否则「公司员工恰好是 admin」会掉回 50 次。方案里把顺序写成显式编号规则。
- **别只列一个校验点/拼接点**：同一配额常在多个策略类里各校验一次，同一段约束常在多个 Service 里各拼一次，漏一个就等于方案不完整；只 grep 常量名也不够，要顺分发入口把调用点找全。
- **方案里不要出现「已改」「已落地」这类措辞**，也不要顺手改一个「很小」的文件——一旦动了代码，这轮评审就失效了。

## Verification

- `git status` 应显示本轮没有任何源码/配置改动（只有用户要求落盘的方案文档，或完全干净）。
- 现状表每一行都有 `文件:行号`，且行号能在对应文件里对上；维度与本次改动面匹配——配额类覆盖限额来源、每个校验点、每个计数写入点；常量/拼装类覆盖常量、唯一分发入口、每个拼接点以及明确不动的旁路。
- 用户已经回答「是否落地」和「关键契约」两个问题，回答被写进了方案的结论/契约小节。
- 方案里的契约与用户选项一致（例如选了 unlimited 布尔，就明确写出不限时 `limit`/`remaining` 为 `null`；选了 PUBLIC 空串不动，方案里就显式排除该分支）。
- 方案含「明确不做的事」，且回答里出现过「代码零改动」的明确声明。
